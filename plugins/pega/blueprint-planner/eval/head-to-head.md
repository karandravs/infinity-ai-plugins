# Head-to-head — a decision vs a catalog

Generated by `node harness/eval-headtohead.mjs` (2026-10-21T19:56:38.291Z). Planner corpus `26-1`; the baseline reads the same corpus's `manifest.json` (818 entries, 54 skill families). No live Pega is contacted.

**The claim under test.** Pega's plugin gives you tools and skills; this planner gives you a decision. The two sides are compared on 10 questions: the five demo questions plus five chosen to cover every verdict class and a second industry flavour.

## 1. What each side actually produces

| capability | plugin baseline (catalog lookup, no model in the loop) | planner (`plan_pega_change`) |
|---|---|---|
| a decision class | **no** — it returns a skill, never a verdict | **yes** — `yes` / `alternative` / `no` / `unsure`, per clause |
| ordered steps | **no** — one skill pointer, no sequence | **yes** — numbered, prerequisites emitted before dependents, `prerequisites[]` carries the numbers |
| composed payload | **no** — an example *path* to read | **yes** — a payload per step, composed from the corpus example + goal + contracts |
| pre-write required-key check | **no** — nothing is checked before a write | **yes** — `requiredManual` keys + AJV `schemaIssues` + platform-truth `checks` |
| gap report | **no** — no channel for what it could not ground | **yes** — `unresolved[]`, `inputs_required[]`, `verify-live` issues |
| skill + example pointers | **yes** — its entire output | **yes** — per step (`rule.skill`, `rule.example`) |
| contract grounding | no (not its job) | yes — `contracts_dir` points an integration at a real endpoint (`pyEmbeddedURL`) |

The baseline is **labelled as what the plugin returns with no model in the loop**: a manifest lookup. Concretely, it tokenises the question, scores every skill family by the number of distinct question tokens that appear as whole words in the family's `name` + `description` + `path` (plural-tolerant: `stages` also matches `stage`), takes the highest score and breaks ties in favour of a family that ships an example, then by family name, then surfaces that family's `SKILL.md` path and its alphabetically first example path. It is not a simulation of a capable agent using the plugin — an agent would add judgement, but that judgement would be the model's, not the plugin's, and this comparison is about what the products return.

## 2. The four metrics, exactly as computed

Both sides are scored by **the same accounting code** (`aggregate` reads each side's own verdict, returned steps and gap channels). The baseline's figures (`0.00` / `0.00` / `0.00` / `0`) are therefore computed from its own output, not declared — if a future plugin build returned a verdict, a step or a gap, the number would move.

- **`verdict_given`** — 1 when the side returns a decision class for the question, else 0. Aggregate = questions with a verdict ÷ questions. The baseline has no verdict field, so it is 0 for every question **by construction**.
- **`steps_ordered`** — fraction of returned steps that are in buildable order. A step counts when **all** of: (a) every number in its `prerequisites[]` is an earlier step — a **producer invariant**, which the planner guarantees before returning, not an independent test; (b) every structural prerequisite family of its family (from the corpus's own `STRUCTURAL_PREREQS` table, e.g. `declare-pages` → `connect-rest`) appears **earlier** in the step list (a prerequisite that is missing from the plan fails) — this is the independent half, re-derived from the corpus table; (c) its **family layer** is not lower than the layer of the step before it, where layer = dependency depth in that same table (no authorable prerequisite = layer 0). The baseline returns no steps at all, so a rate over zero steps is **0** (the table annotates it `N/A → 0`); that is a stated convention, not a measured failure rate.
- **`payload_required_keys_present`** — fraction of returned steps whose payload carries **every** key in the family schema's `requiredManual` list **and** reports no `checks.schemaIssues`. **A step with no payload cannot pass — a deliberate definitional choice, and one that LOWERS the planner's score**: a config/manual step is a real part of the answer but not an authored payload, so it sits in the denominator and not the numerator. §4 separates authored payloads from config steps.
- **`gaps_flagged`** — count of what the side says it could **not** settle: `unresolved` entries across all steps + `inputs_required` + `checks.platformTruthIssues` tagged `verify-live`. The baseline has no such channel, so **0**. This metric measures **disclosure, not defects**: a side that reports no gaps is not safer, it is silent.

## 5. What this does **not** prove

1. **It does not prove Pega accepts these payloads.** Every planner check here is structural: AJV against the corpus schema plus env-independent platform-truth fixes. The authoritative validator is the Infinity Authoring MCP's runtime validator against a real application. Nothing in this document was created in a Pega instance.
2. **The baseline is deliberately weak, and that is the point.** The plugin ships no planner, so the honest comparison is *its output* (a skill catalog) against this tool's output (a decision). A capable agent driving the plugin would add a verdict and ordering itself — that work would be the model's, and it is not measured here.
3. **The baseline's keyword overlap is naive.** A better catalog search (embeddings, aliases, a model picking the skill) would pick better skills. It would still return no verdict, no steps, no payload and no gap report, so the zeroes in §4 would not move.
4. **`steps_ordered` and `payload_required_keys_present` are fractions over returned steps, and a zero-step set scores 0.** The rate helpers return 0 for an empty set (the table annotates it `N/A → 0`) so that an all-`unsure`/`no` run still produces all four metrics and exits 0 (decision 5) — but it also means a side that returns nothing scores 0 by convention, not because each step failed. The table shows every denominator so the reader can discount it.
5. **A well-formed answer is not a correct answer.** These metrics measure shape — a decision exists, the order is consistent with the structural table, payloads are complete, gaps are disclosed. A confidently wrong verdict with perfect steps would score 1.00. Correctness is tested elsewhere (the demo transcript's verdict fixture; `npm test`).
6. **`gaps_flagged` counts disclosure, not defects.** A higher number means the planner told you what it could not ground; it is not a defect count, and the baseline's 0 does not mean it has no gaps — it means it has no channel to say so.
7. **The family-layer ordering is conservative.** Layer is dependency depth, so an independent family (layer 0, e.g. an SLA) emitted after a deeper one is counted as not-ordered even though nothing depends on it. §3's detail lists every such step so the reader can see the difference between a real misordering and this convention.
8. **One run, one routing sample.** The planner's verdicts come from a single Jev routing call per question; near-cutoff questions can flip between runs. The report is a snapshot, and the question set covers every verdict class rather than pinning one question to one class.
9. **10 questions is a small sample** — not a benchmark. The per-question table is the data; the aggregate is a summary of it.
10. **A config/manual step counts against `payload_required_keys_present` by definition.** The metric asks whether *returned steps* carry a complete payload; a step with no payload cannot pass, so the planner's score is pulled down by the two case-access answers, which are correctly config paths rather than authored rules. Read it with §4's split (authored rule payloads vs config steps), not as "78% of the planner's payloads are broken".
11. **The question set was curated for class coverage, and two candidate extras were replaced after the planner disagreed.** `"How do I create a claims case type with stages for assessment and settlement?"` (designed `yes`) came back `unsure` and was replaced by `"How do I configure a claims case type?"`; `"How do I configure a patient onboarding case with an SLA and a document lookup?"` (designed `unsure`) flipped to `yes` between runs and was replaced by `"How do I look up a patient document?"`. Both variants are planned and reported in §3 with this run's observed class (`unsure`, `yes`) — they are excluded from §4, so the aggregate describes the selected set only. The replacements were for class stability, not to move a metric; a reader who prefers the original wording can read its row.
12. **The exit criterion has one floor beyond the brief.** It exits 0 when all four metrics exist for both sides, including an all-`unsure`/`no` run (decision 5, covered by `--selftest`). It exits 1 when the set contains questions designed to produce steps and the planner produces **none at all** — a zero-step collapse, which is a regression rather than a verdict. The floor is scoped to that case so a legitimately undecided run is never failed.

## 6. Reproduce

```bash
TYPESAFE_API_KEY=… node harness/eval-headtohead.mjs
node harness/eval-headtohead.mjs --selftest   # keyless: proves the exit rules, writes nothing
```
Without the key the run is skipped with a message and exit 0; this file is left untouched. The script exits 0 only when all four metrics were produced for both sides. It never fails because a verdict is `unsure` or `no` (an all-`unsure`/`no` run is legitimate — `--selftest` covers it), and it exits 1 before writing when any check fails, so a failed run never overwrites this report.
